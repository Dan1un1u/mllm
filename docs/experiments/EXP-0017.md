# EXP-0017 — Native U8 GroupQueryAttention lowering

## Hypothesis

QAIRT 2.49 native U8 GroupQueryAttention can preserve compiler-owned HMX/HVX/VTCM scheduling and execute the fixed layer-14 s32/context-1024 attention region faster than the accepted RMSNorm-A8 baseline decomposition.

## Primary physical variable

Replace only the post-Q/K-RMSNorm and post-RoPE QK-to-causal-mask-to-Softmax-to-AV region, including KV cache update and GQA head expansion, with qti.aisw::GroupQueryAttention; keep W4G32 LPBQ projections, asymmetric U8 activations, native U8 RMSNorm, QAIRT 2.49, P19, inputs, qparams, and compared external tensor boundary fixed.

## Hard gate

On PJZ110, for layer 14, s32/context-1024, the candidate must compile and lower as native U8 GroupQueryAttention on HTP without CPU fallback or graph split, preserve valid shape/cache/causal semantics, and achieve median end-to-end device wall latency no greater than the current decomposed native attention over the exact same external boundary with all required layout/cache transformations included. Report local error against both current W4A8 and W4A16 references; error is diagnostic unless semantics are invalid. If the speed gate fails, stop before layer or full-model integration.

## Evidence profile

micrograph-performance

## Fixed experiment scope

- Toolchain and hardware: QAIRT 2.49.0.260730, PJZ110 / SM8750 / HTP V79.
- Lineage: branch from the accepted `codex/w4a8g32-rmsnorm-u8-qairt249` baseline selection commit.
- Shape: Qwen3 middle layer 14, prefill `S=32`, existing cache length `1024`.
- Candidate boundary: post-Q/K RMSNorm and post-RoPE Q/K/V tensors through the final attention output before `o_proj`.
- Q/K RMSNorm and RoPE remain outside the candidate because Qwen3 applies Q/K RMSNorm before RoPE and the native op has no Q/K RMSNorm parameters. The candidate therefore uses separate Q/K/V input mode with `do_rotary=0`.
- The comparator uses the accepted baseline decomposition over exactly the same boundary: cache update, GQA head expansion, QK, scale, causal mask, native Softmax, AV, and required layout transforms.
- Projection layers, LPBQ encodings, activation qparams, RMSNorm implementation, and `o_proj` are outside the experiment and must not change.

## Milestones and stop rule

1. Compile a U8 `qti.aisw::GroupQueryAttention` micrograph and audit the finalized graph for native HTP lowering, shape compatibility, and absence of CPU fallback or graph split.
2. Run deterministic real layer-14 inputs and report local error versus the current W4A8 decomposition and the precision-usable W4A16 comparator. Numerical error is diagnostic, but invalid cache, masking, or causal semantics is an implementation failure.
3. Measure median device wall latency for candidate and comparator with identical graph boundaries and iteration policy. Optrace work cycles are explanatory only and are not the speed gate.
4. If candidate latency is slower, stop and close the experiment without layer or full-model integration. Only a passing micrograph may proceed to a later, separately approved integration stage.

## Outcome

Completed as a valid negative compile-gate result on 2026-08-25. The selected
W4A8 baseline and all comparator roles remain unchanged. No device performance
or numerical result is claimed because the candidate could not produce a
finalized HTP context.

### Implemented probe

- Source commit: `a8fe651ccea933d46e7c690c2541ba609cfb83f9`.
- The experiment-only mllm marker lowers directly to
  `qti.aisw::GroupQueryAttention` with 16 query heads, 8 KV heads, head size
  128, asymmetric U8 Q/K/V/cache/output tensors, and the fixed layer-14
  `S=32`, context-1024 shapes.
- The primary form uses separate post-RoPE Q/K/V inputs, growing cache,
  `do_rotary=0`, and `scale=1/sqrt(128)`. A full ten-tensor RoPE signature and
  official ONNX/QDQ probes were also implemented strictly as compile
  diagnostics.
- Both the AOT compiler target and the device runner target build successfully;
  the ONNX generator and output-analysis scripts pass Python syntax checks.

### Compile-gate evidence

1. The primary seven-tensor mllm graph passes frontend/basic validation but
   fails during HTP graph finalization. QAIRT reports that no physical
   properties are registered for `q::QNN_GroupQueryAttention` and cannot create
   the op.
2. The official QNN converter successfully emits the same logical
   `GroupQueryAttention`, but both `libQnnHtp.so` and `libQairtHtp.so` context
   generation fail at the same physical op-creation point. This independently
   excludes the mllm visitor as the cause.
3. The failure remains with static cache, growing cache, no past cache,
   `scale=0`, explicit `scale=1/sqrt(128)`, retained U8 QDQ, SM8750/V79, and an
   SM8850/V81 control. The newer QAIRT DLC prepare path also fails at the same
   physical lowering boundary.
4. Packed-QKV mode fails earlier in the official converter because its omitted
   optional key/value slots are treated as references to an empty tensor name.
   It therefore does not provide an alternative compilable form.
5. The full RoPE form exposes a second independent package inconsistency. The
   master op definition requires `position_ids` as INT64, while the HTP
   supplement advertises an INT32 combination. The official converter
   downcasts INT64 to INT32 and is then rejected by its master validation. An
   mllm INT64 probe satisfies the master contract but is rejected by the HTP
   validator with `None of the combinations match the provided case`.

The QAIRT 2.49 package therefore contains public op definitions, optimizer
symbols, and U8 HTP constraints for GroupQueryAttention, but no input form found
under the documented contracts can be finalized as a usable HTP graph in this
toolchain. This is a toolchain capability/contract failure rather than a
performance failure of a runnable kernel.

The mandatory first milestone failed, so the stop rule was applied before
device deployment, numerical comparison, timing, Optrace, layer integration,
or full-model integration. Execution is `completed`, evidence validity is
`valid`, local gate is `fail`, and project adoption remains `pending` until the
user records a decision.
