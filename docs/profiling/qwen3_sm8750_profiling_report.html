摘要

本工作建立了一套面向 Qualcomm HTP 的结构化 profiling 方法：将 QNN Optrace、QHAS dominant path、HTP 资源标签、时间区间 union、内存计数器以及编译期 Quantization Manifest 对齐到 Qwen3 的实际网络结构。核心原则是：异构引擎上的累计 cycles 表示工作量，而非可直接相加的端到端延迟；性能判断必须回到依赖图上的关键路径。

1. SM8750 Hexagon NPU：并行的 HVX、HMX 与数据搬运

SM8750（Snapdragon 8 Elite）的 Hexagon NPU 采用 fused AI accelerator 架构，公开规格列出 Scalar Accelerator、Tensor Accelerator、HVX、Micro Tile Inferencing 与 Hexagon Direct Link，并支持 INT4、INT8、INT16 与 FP16 精度 [1]。在本次 V79 Optrace 中，Tensor Accelerator 以 HMX 资源出现，向量侧以 6 条 HVX lane 出现。

HVX 是宽 SIMD 向量执行单元；Qualcomm 的 HVX 编程手册明确说明多个 hardware thread/vector context 可并行执行 [2]。更重要的是，本次 trace 直接观测到 HMX、6 条 HVX、DMA 与同步事件在时间轴上重叠，跨 Q projection 的量化子事件最大并行度达到 7。因此，下面的关系是 profiling 的出发点：

Σ(event cycles across HMX/HVX/DMA) ≠ graph latency
不要简单累加 cycles：同一时刻可能有多个 HVX kernel、HMX MAC 与 DMA 同时工作。累计 cycles 可用于衡量资源工作量和优化价值，但只有 wall/timeline、interval union 与 dependency critical path 才能回答延迟问题。

s32 中所有 HTP event 的累计工作量为 221.8M cycles，但 HTP timeline 只有 46.6M cycles，二者相差 4.76×；s1 的对应差距为 4.81×。如果直接把每个 operator 或每个 engine 的 cycles 相加，会把并行重叠错误地计为串行延迟。

QHAS 给出 HTP0 的 dominant path 归因；我们将其中的 direct/partial contribution 映射回 QNN node，再按 Qwen3 stage 聚合。partial 表示一个 event 只有部分区间位于关键链上，不是独立硬件，也不是 CPU fallback。

关键路径是如何得到的？

  1. 使用 schematic 将 runtime resource ID 还原为 QNN node 与 HTP kernel。
  2. 读取每个 HTP event 的时间戳、duration、依赖输入、resource lane 与 dominant-path contribution。
  3. 由官方 QHAS 的 Dominant Path HTP0 得到依赖/资源约束下的关键链；再把 direct contribution 聚合到 Qwen3 stage。
  4. 同时对原始 Chrome Trace 做时间区间 union，检查同类 kernel 内部以及 HMX/HVX/DMA 之间的重叠。
  5. 用 Quantization Manifest 补充 pre-finalize QNN tensor 的 logical dtype、carrier dtype、scale/zero-point 与 blockwise encoding；用 Optrace 补充 post-lowering physical I/O dtype。
执行位置边界：出现在本报告 Optrace/QHAS 中的节点位于 HTP graph 内，trace 中没有 CPU execution resource，也没有 graph fallback 错误。但 HTP Optrace 不能证明 QnnGraph_execute 之外不存在 CPU 工作；tokenization、sampling、RPC/runtime 和 tensor setup 需要 Android Perfetto/CPU trace 补充。

QKᵀ 和 Softmax 的 DRAM 计数为零并不意味着“没有内存开销”；它们主要使用 VTCM。VTCM 是 HTP 的片上 tightly coupled scratchpad，tile 和中间结果会反复读写，因此 VTCM traffic 可显著大于 DRAM traffic。整体 s1 的 DRAM read/write 约为 1.051 GB / 2.60 MB，而 VTCM read/write 约为 9.908 GB / 11.681 GB。

关于 memory-bound：这些数据支持“projection 是权重流/格式转换主导，attention reduction 是片上 VTCM 数据流主导”的判断，但还不是完整 roofline 证明。严格区分 compute-bound 与 memory-bound 仍需受控频率下的有效带宽、MAC 吞吐与 stall counter。

4.3 RMSNorm、RoPE 与 elementwise

RMSNorm、RoPE、residual、SiLU/product 主要落在 HVX。单个 stage 的关键路径占比不高，但它们决定了 activation 的量化边界，并影响能否在层间持续保持低比特表示。若未来 W4A4 只覆盖 projection、却在每个 RMSNorm/RoPE/residual 边界反复升降精度，转换开销仍会重新出现。

5. 量化视角：W4A16 的真正代价在哪里

编译期 Manifest 与 runtime Optrace 揭示了两个不同层次的数据类型：

post-lowering HTP
HVX：W4 block scale → physical QInt8

Conv2d_w_blk_exp_scale 不是图像卷积，也不是 CPU fallback；它是 QNN 对 LPBQ quantized linear 的 lowered 表达。每个 graph 有 1,009 个 LPBQ weight tensor。V79 在 HVX 上将逻辑 W4 block-scaled weight 展开为 per-channel QInt8，然后交给 HMX MAC。

最醒目的现象是：W4 展开 work 是 HMX MAC work 的 16.7×。由于六条 HVX 并行，它不等于 16.7× 的延迟；但 W4 展开本身仍贡献了约 34.2% 的 HTP dominant timeline。换言之，当前 W4A16 路径通过节省权重存储换取了显著的 runtime unpack/dequant、staging 与格式转换成本。

5.2 W4A4：从“低比特存储”走向“低比特直接执行”

研究假设：结合已有“利用 8-bit HMX 数据通路实现 Int4 乘法”的研究，如果能够让 activation 与 weight 以 W4A4 packed form 跨层保存，并在 HMX 路径直接完成等价 Int4 MAC，就可能同时减少 W4→QInt8 展开、A16 搬运、VTCM footprint 以及部分 signed/requant conversion。真正的目标不是只把模型文件压到 4 bit，而是避免执行前后反复恢复为 8/16 bit。

6. 总结与后续研究方向

总体结论

  1. HTP 是并行异构流水线。HMX、6 条 HVX、DMA 与同步同时活动，累计 work cycles 远高于 wall cycles。
  2. 性能归因必须基于关键路径。work cycles 用于排序资源消耗，dominant path 用于定位直接延迟贡献，interval union 用于校验重叠。
  3. Qwen3 的关键路径由权重密集 projection 主导。MLP 与 LM head 占约三分之二，Q/K/V/O projection 次之。
  4. 当前量化瓶颈是“转换与数据流”，不是 HMX MAC 本身。W4 block expansion、DMA/VTCM staging 和 signed conversion 的工作量及关键路径贡献均显著。
  5. W4A4 的研究价值在于直接执行。如果低比特表示能跨 operator 保持并直接进入 HMX，潜在收益不仅来自容量下降，更来自消除中间格式恢复。

建议的研究路线

  1. 实现 direct W4A4 HMX kernel。利用现有 8-bit HMX Int4 乘法机制，明确 packed layout、cross-term correction、accumulator 与 requant 方案。
  2. 让低比特 activation 跨 operator 存活。优先覆盖 MLP gate/up/down、Q/K/V/O 与 LM head；避免每层进入 projection 前重新量化。
  3. 消除 W4 runtime expansion。比较 direct packed consumption、离线预展开/预排布和按 tile cache 三条路线；量化 DRAM、VTCM 与启动成本。
  4. 优化 HMX/HVX/DMA 调度。采用 double buffering、tile prefetch 与更长的 producer-consumer pipeline，使剩余转换隐藏在 HMX MAC 后方。
  5. 处理 attention 特有转换。重点减少 QKᵀ/Attn×V 的 convert_weights_to_signed.shuffled，并评估 A4 KV cache 或混合精度 cache。
  6. 建立准确率—延迟—能耗联合评估。在相同模型、频率、温度和 batch/sequence 条件下比较 W4A16、W4A8、W4A4；profile-off 重复计时，Optrace 只用于归因。
  7. 补齐系统边界。用 Perfetto/FastRPC markers 测量 QnnGraph_execute 之外的 CPU/RPC/tensor setup，从 graph-level 扩展到 token-level end-to-end。

7. 可信度、限制与可复现材料

  • 本报告基于一次 graph-filtered Optrace sample。Optrace 会扰动执行；性能结论需用 profiling off、多次 warmup/repetition 与受控频率验证。
  • 原生 V79 context 已确认改变 lowering/scheduling；本报告不再使用 SM8650/V75 compatibility context。
  • schematic 是由相同 V79 graph definition 重新 finalize 生成并成功无 unknown-resource 解码；严格 bit-for-bit provenance 的后续实验应把 context 与同一次 finalize 的 schematic 一起归档。
  • dominant-path contribution 是直接归因，不是删除 operator 后的反事实收益；W4A4 上界必须通过实际新图验证。
