为什么 process CPU / wall 可以大于 1？它是进程全部线程 CPU 时间的总和；多个 host/RPC/polling 线程可以并行。调用线程约占半个 CPU 核，与当前 setRpcLatencyAndPolling() 的低延迟轮询策略相符。这是图调用期间的 host 开销，不等价于某个 QNN node 改在 CPU 上计算。

这些 wall time 来自启用审计、未控温控频的一次功能性运行，只用于界定 CPU 活动，不替代原 Optrace 或关闭审计后的性能基线。

判定逻辑

  1. 若图内算子被 QNN CPU backend 执行，进程必须具备对应 backend 实现；本次初始化及每次执行后均未发现 libQnnCpu.so。
  2. 旧 Optrace 中 s1/s32 的可映射 QNN 节点执行域全部为 HTP，资源为 HMX/HVX/DMA/sync；没有 CPU execution resource。
  3. 运行日志没有 graph execution failure 或 fallback 信息，模型成功完成 prefill/decode。
  4. 因此当前证据支持“没有图内 CPU fallback”。CPU 时间只说明 CPU 在协助提交、轮询和同步，不能推翻前三项证据。

严格边界：若未来把模型拆成一个 HTP graph 加一个显式 mllm CPU graph，后者不属于 QNN graph 内 fallback，需要在 dispatcher/应用级 trace 中单独统计。本报告没有把这种图外工作隐藏掉。
